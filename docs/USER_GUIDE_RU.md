## 1. Назначение XPAM Script

XPAM Script — это установщик и набор эксплуатационных команд для подготовки чистого VPS под VLESS, Telegram proxy / MTG, 3x-ui, Xray, HAProxy, nginx, Let's Encrypt, SSH-защиту, диагностику и регулярное обслуживание.

Цель скрипта — дать пользователю готовую рабочую схему с минимальным количеством ручной настройки. Пользователь готовит VPS, домены и SSH-ключ, запускает bootstrap, проходит меню и получает сервер, который можно проверять, обслуживать, обновлять и восстанавливать понятными командами.

- VLESS работает через домен и публичный порт 443.
- Telegram proxy / MTG работает через отдельный домен и тот же внешний HTTPS-порт 443, без отдельного публичного MTG-порта.
- Панель 3x-ui закрыта отдельным путём, Basic Auth и собственным логином/паролем 3x-ui.
- HAProxy и nginx формируют нормальную HTTPS-поверхность: домены открываются как обычные сайты, а не как пустой технический сервер.
- Health-check, deep-health, repair и weekly maintenance помогают понять, что сервер живой и не сломан после обновлений.
- DoubleHop Mode позволяет на Entry-сервере отправить VLESS, Telegram или оба типа трафика через отдельный Exit-сервер.

> [!WARNING]
> XPAM Script не обещает абсолютную невидимость и не заменяет здравый смысл. Домен, DNS, SSH-ключи, пароли, VLESS-клиенты, Telegram secret и Exit-сервер должны быть настроены аккуратно.


### 1.1. Как это устроено, в двух словах

Снаружи у сервера открыт всего один «рабочий» порт — обычный HTTPS-порт 443, тот же, что у любого сайта. Всё, что приходит на него, разбирается по имени домена и отправляется дальше:

```text
Интернет → порт 443 (HTTPS)
             │
             ├── ваш VLESS-домен      → подключение VLESS
             ├── ваш Telegram-домен   → Telegram proxy
             └── любой другой запрос  → обычный сайт (маскировка)
```

Отсюда два важных следствия:

- **Со стороны сервер выглядит как обычный веб-сервер.** Если кто-то откроет ваш домен в браузере, он увидит нормальный сайт, а не пустую страницу и не ошибку. Это и есть маскировка (глава 17).
- **Отдельных «подозрительных» портов нет.** Ни VLESS, ни Telegram-прокси не занимают собственный публичный порт — всё идёт через 443.

Панель управления 3x-ui тоже доступна через 443, но по скрытому адресу и под двумя паролями, поэтому случайно на неё не наткнуться.

## 2. Что нужно подготовить до запуска

Перед запуском XPAM Script подготовьте чистый VPS, домены, SSH-ключ и доступ к DNS-панели. Если пропустить этот этап, установка может остановиться на certbot, SSH-безопасности или health-check.

| Что подготовить | Зачем это нужно |
|---|---|
| Чистый VPS | Ubuntu или Debian. Не используйте сервер с чужими production-сайтами, ручными nginx/HAProxy/Xray-конфигурациями или старой 3x-ui установкой. |
| Домен | Нужен хотя бы один домен. Для полной схемы удобнее иметь root/www, VLESS/panel-домен и Telegram-домен. |
| Доступ к DNS | Вы должны уметь создать A-записи на публичный IPv4 VPS. |
| SSH-доступ root | На первом входе обычно используется пароль провайдера, но до шага 1 нужно настроить вход по SSH-ключу. |
| Порты | TCP 22 для SSH, TCP 80 для Let's Encrypt, TCP 443 для HTTPS/VLESS/Telegram proxy. |
| Память | Скрипт рассчитан и на малые VPS, но 1 GB RAM комфортнее, чем 512 MB. На слабых VPS XPAM старается уменьшить нагрузку. |
| Ещё один домен (по желанию) | Понадобится, только если позже захотите включить запасной транспорт (глава 16). Сразу он не нужен. |

- Не ставьте заранее nginx, HAProxy, Xray, 3x-ui, certbot или отдельный Telegram proxy руками. XPAM сам поставит и свяжет нужные компоненты.
- Не добавляйте managed-домены XPAM в /etc/hosts на 127.0.0.1 или 127.0.1.1. Домены должны указывать на публичный IPv4 VPS.

> [!WARNING]
> XPAM работает с обычным SQLite backend 3x-ui: /etc/x-ui/x-ui.db. Не переключайте 3x-ui на PostgreSQL вручную, иначе health/repair не смогут безопасно читать текущую конфигурацию.

## 3. SSH-ключ обязателен до запуска скрипта

Шаг 1 отключает SSH-вход по паролю. Поэтому до запуска XPAM Script пользователь обязан создать SSH-ключ, добавить public key на VPS и проверить вход по private key. Это не рекомендация, а обязательное условие.

Работать можно через MobaXterm, PuTTY, Termius, Windows Terminal / PowerShell или OpenSSH в Linux/macOS. Основной пример ниже дан через MobaXterm, потому что в нём удобно создать ключ и сразу настроить сессию.

> [!CAUTION]
> Private key хранится только на вашем компьютере. Его нельзя отправлять в чат, тикет, скриншот, GitHub issue или чужой сервер. На VPS добавляется только public key.


### 3.1. Создать первую SSH-сессию в MobaXterm

- Откройте MobaXterm и нажмите Session.
- Выберите SSH.
- В поле Remote host введите IPv4-адрес VPS: SERVER_IP.
- В поле Username укажите root.
- Port оставьте 22 и нажмите OK.
- При первом подключении сервер попросит пароль от VPS. Введите пароль, который выдал провайдер.

После успешного входа оставьте эту SSH-сессию открытой. Она нужна как страховка, пока вы настраиваете вход по ключу.


### 3.2. Создать SSH-ключ в MobaXterm

- Не закрывая SSH-сессию с сервером, откройте Tools -> MobaKeyGen.
- Тип ключа выберите ED25519. Это современный короткий ключ, который удобно использовать для SSH.
- Если ED25519 недоступен, используйте RSA 4096.
- Нажмите Generate и двигайте мышью в окне генератора, пока ключ не будет создан.
- Сохраните private key в безопасное место на своём компьютере.
- В окне MobaKeyGen скопируйте public key из поля Public key. Он обычно начинается с ssh-ed25519.

> [!IMPORTANT]
> Лучший вариант — ED25519. RSA 4096 используйте только если клиент или старый сервер не поддерживает ED25519.


### 3.3. Добавить public key на VPS

Вернитесь в открытую SSH-сессию MobaXterm, где вы вошли на сервер по паролю. Все команды в этом пункте выполняются именно на VPS, а не на Windows-компьютере.

```text
mkdir -p /root/.ssh
chmod 700 /root/.ssh
nano /root/.ssh/authorized_keys
```

Откроется редактор nano. Вставьте туда public key из MobaKeyGen. Ключ должен быть одной строкой и начинаться с ssh-ed25519 или ssh-rsa. Пример ниже показывает только формат строки; копировать его как свой ключ нельзя.

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... user-comment
```

Сохраните файл в nano: Ctrl+O, Enter, затем Ctrl+X. После этого задайте правильные права:

```text
chmod 600 /root/.ssh/authorized_keys
```

Команда chmod 600 задаёт безопасные права на файл authorized_keys. У некоторых провайдеров вход может работать и без неё, но для SSH это правильная настройка.


### 3.4. Настроить вход по private key в MobaXterm

- Откройте настройки сохранённой SSH-сессии вашего VPS в MobaXterm.
- Перейдите во вкладку Advanced SSH settings.
- Поставьте галочку Use private key.
- Выберите private key, который вы сохранили в MobaKeyGen.
- Нажмите OK и подключитесь к серверу заново.

Если всё настроено правильно, новая сессия откроется по private key. Старую парольную сессию пока не закрывайте: сначала проверьте новый вход.


### 3.5. Проверить вход по ключу

Откройте новую SSH-сессию к серверу через MobaXterm с выбранным private key и выполните на VPS:

```text
whoami
hostname
```

Ожидаемо whoami должен вывести root, а hostname — имя вашего VPS. Только после этого можно переходить к запуску XPAM Script.

> [!WARNING]
> Если новая сессия не открылась по ключу, не запускайте шаг 1. Сначала исправьте ключ, путь к private key или содержимое /root/.ssh/authorized_keys.


### 3.6. Для пользователей Windows Terminal / PowerShell

Этот вариант нужен тем, кто работает не через MobaXterm, а через встроенный OpenSSH в Windows. Команды в этом пункте выполняются на локальном Windows-компьютере.

```text
ssh-keygen -t ed25519 -C "xpam-vps"
type $env:USERPROFILE\.ssh\id_ed25519.pub
```

Скопируйте public key целиком и добавьте его на VPS в файл /root/.ssh/authorized_keys. Проверка входа с локального Windows-компьютера:

```bash
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@SERVER_IP
```


### 3.7. Для Linux/macOS

На локальном компьютере Linux/macOS выполните:

```bash
ssh-keygen -t ed25519 -C "xpam-vps"
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@SERVER_IP
ssh -i ~/.ssh/id_ed25519 root@SERVER_IP
```

> [!IMPORTANT]
> После шага 1 парольный вход будет отключён. Держите одну старую SSH-сессию открытой до полной проверки новой сессии по ключу.

## 4. Как подготовить DNS

Домены должны быть готовы до certbot и health-check. Let's Encrypt выдаёт TLS-сертификаты на домены, а nginx, HAProxy, Xray и Telegram proxy / MTG используют эти имена для HTTPS-поверхности, SNI-маршрутизации и ссылок подключения.

В DNS-панели регистратора или DNS-провайдера создайте A-записи. Все домены, которые вы будете вводить в XPAM Script, должны указывать на IPv4-адрес VPS.

```text
example.com        A    SERVER_IP
www.example.com    A    SERVER_IP
vless.example.com  A    SERVER_IP
tg.example.com     A    SERVER_IP
```

| Назначение | Пример | Комментарий |
|---|---|---|
| Root domain | example.com | Основной сайт-маскировка. Нужен в профиле с root-сайтом. |
| WWW alias | www.example.com | Обычно ведёт на тот же сайт, что root domain. |
| VLESS / panel domain | vless.example.com | Домен для VLESS, панели 3x-ui и команды links. |
| Telegram domain | tg.example.com | Домен для Telegram proxy / MTG. |

- TTL на время настройки можно поставить 300-600 секунд.
- Если DNS ещё не распространился, certbot может не получить сертификаты.
- AAAA-записи не обязательны. Не создавайте их, если не уверены, что IPv6 правильно настроен у VPS-провайдера.
- Не привязывайте домены XPAM к localhost в /etc/hosts.

Проверить DNS можно с вашего компьютера или с VPS:

```text
nslookup example.com
nslookup vless.example.com
nslookup tg.example.com
```

> [!WARNING]
> Если nslookup показывает старый IP или NXDOMAIN, не запускайте установку. Сначала дождитесь корректного DNS.

## 5. Загрузка и первый запуск через GitHub bootstrap

Обычный пользователь устанавливает XPAM Script через GitHub bootstrap. Вручную загружать архивы, выбирать sha256-файлы или распаковывать комплект не требуется. Bootstrap скачивает актуальный release archive, проверяет контрольную сумму и запускает установщик.

Команды ниже выполняются на VPS под root после подготовки SSH-ключа и DNS:

```bash
cd /root
curl -fsSL https://raw.githubusercontent.com/deepru/xpam-script/main/bootstrap.sh -o xpam-bootstrap.sh
sudo XPAM_REPO="deepru/xpam-script" bash xpam-bootstrap.sh
```

- Запускайте bootstrap только на чистом VPS, подготовленном по разделам 2-4.
- Не редактируйте bootstrap.sh перед запуском, если не понимаете, зачем это нужно.
- Если bootstrap не может скачать release, сначала проверьте DNS, доступ VPS к GitHub и системное время.
- После запуска следуйте меню: сначала пункт 1, затем пункт 2. Пункт `0` — это выход.

> [!CAUTION]
> Не скачивайте случайные архивы из чатов. Для обычной установки используйте GitHub bootstrap из официального репозитория проекта.

## 6. Шаг 1: SSH-безопасность и prefix

Перед этим шагом уже должен быть выполнен раздел 3: public key добавлен на VPS, private key выбран в SSH-клиенте, а вход по ключу проверен отдельной новой сессией.

В меню выберите **пункт 1 «SSH-безопасность и создание команды сервера»**. На этом этапе скрипт проверяет SSH-доступ по ключу, просит задать SERVER_PREFIX, создаёт prefix-команду и готовит безопасную основу для дальнейшей установки.

Скрипт спросит, проверяли ли вы вход по SSH-ключу в отдельной сессии. Отвечать `yes` можно только если вы это действительно сделали: сразу после этого вход по паролю отключается.

- Отключается вход по SSH-паролю.
- Оставляется вход по SSH-ключу.
- Отключается X11 forwarding.
- SSH-туннели остаются разрешёнными, если нужны для эксплуатации.
- Публичный SSH приводится к IPv4-only политике XPAM.
- Если hostname от провайдера не резолвится и sudo ругается, скрипт нормализует /etc/hosts.
- Префикс сохраняется в /etc/xpam-script/prefix.env и используется во всех дальнейших командах.

Prefix — это короткая метка сервера. Например, если prefix равен tr, основные команды будут выглядеть так:

```bash
sudo tr-xpam
sudo tr-links
sudo tr-health
sudo tr-repair
```

> [!IMPORTANT]
> Основная команда управления — <prefix>-xpam. Старое install-имя не используется как пользовательский основной интерфейс.

Если после шага 1 скрипт просит перезагрузку, выполните:

```bash
sudo reboot
```

После перезагрузки зайдите на VPS снова по SSH-ключу и продолжите через:

```bash
sudo <prefix>-xpam
```

## 7. Шаг 2: установка и финальная настройка сервера

**Пункт 2 «Установить / продолжить настройку сервера»** создаёт рабочую схему сервера. Он ставит компоненты, получает сертификаты, создаёт 3x-ui inbound/client, включает Telegram proxy / MTG при выбранной полной схеме, настраивает health, repair и weekly maintenance.

Установка идёт в **два захода с перезагрузкой между ними** — это нормально и так задумано:

1. Первый запуск пункта 2 готовит систему: пакеты, DNS, сеть, firewall, сайты-маскировки, сертификаты и 3x-ui. В конце он попросит перезагрузить сервер и завершится.
2. Вы выполняете `sudo reboot` и заходите обратно по SSH-ключу.
3. Второй запуск того же пункта 2 достраивает схему: nginx, Telegram proxy / MTG, HAProxy, команды и обслуживание.

Пока установка не завершена, пункт 2 из меню не исчезает — он продолжает установку с того места, где она остановилась.


### 7.1. Выбор профиля

XPAM предлагает несколько профилей установки. Выберите тот, что подходит под ваши домены — от минимальной схемы до полной, с сайтом-маскировкой на основном домене.

| Профиль | Когда использовать |
|---|---|
| VLESS + Telegram proxy / MTG на поддоменах | VLESS и Telegram работают на отдельных доменах-поддоменах; отдельного сайта на основном домене нет. |
| Основной домен + VLESS + Telegram proxy / MTG | То же плюс сайт-маскировка на основном домене (root/www); VLESS/панель и Telegram — на своих доменах. |


### 7.2. Какие данные спросит скрипт

- VLESS/3x-ui masking domain — домен панели и VLESS, например vless.example.com.
- Main/root domain — основной домен, если выбран root-профиль, например example.com.
- WWW alias — обычно www.example.com.
- Telegram domain — домен Telegram proxy / MTG, например tg.example.com.
- Email для Let's Encrypt — можно оставить пустым, но лучше указать рабочий email.
- 3x-ui panel path — скрытый путь панели. Не используйте пустой путь, .., /.well-known и очевидные значения.
- Локальные порты nginx, Xray, 3x-ui, Telegram proxy / MTG — обычно можно оставить по умолчанию.
- 3x-ui admin username/password — сохраните эти данные в безопасном месте.


### 7.3. Что делает пункт 2

- Обновляет систему и проверяет состояние apt/dpkg.
- Создаёт swap и облегчённые настройки для малых VPS, если это нужно.
- Проверяет DNS и не ломает рабочий DNS провайдера без причины.
- Настраивает UFW, fail2ban, certbot, nginx, HAProxy, Xray и 3x-ui.
- Получает TLS-сертификаты Let's Encrypt.
- Создаёт VLESS inbound и начального VLESS-клиента в 3x-ui.
- Создаёт Telegram proxy / MTG inbound через 3x-ui, если выбран профиль с Telegram.
- Создаёт сайты-маскировки и служебные маршруты.
- Создаёт команды <prefix>-xpam, <prefix>-links, <prefix>-health и <prefix>-repair.
- Настраивает автоматическое еженедельное обслуживание.

Запасной транспорт (глава 16) при установке не настраивается — его можно включить позже, когда понадобится.

> [!WARNING]
> Если скрипт явно просит reboot, выполните sudo reboot, дождитесь загрузки VPS и продолжите через sudo <prefix>-xpam. Не пытайтесь завершить установку до перезагрузки, если скрипт её требует.

## 8. Что именно меняет XPAM Script на VPS


### 8.1. Безопасность и доступ

- SSH-пароль отключён, вход остаётся только по ключу.
- UFW разрешает публично только нужные TCP-порты: 22, 80, 443.
- fail2ban защищает SSH от перебора и использует systemd backend.
- Панель 3x-ui закрыта Basic Auth на уровне nginx и отдельным логином 3x-ui.


### 8.2. TLS, маршрутизация и маскировка

- nginx отдаёт обычные сайты и служебные endpoints.
- HAProxy принимает публичный 443 и маршрутизирует трафик на нужный локальный backend.
- Xray/VLESS и Telegram proxy / MTG связаны с публичными доменами через 443.
- Let's Encrypt сертификаты выдаются на введённые домены.
- Для каждого домена автоматически создаётся правдоподобный сайт-маскировка (свой на каждом домене), чтобы сервер выглядел как обычный веб-сайт.


### 8.3. 3x-ui

- 3x-ui хранит inbounds, clients и MTG-настройки в /etc/x-ui/x-ui.db.
- XPAM читает текущие VLESS и Telegram links из актуальной конфигурации 3x-ui.
- Текстовые secure-notes остаются для паролей и служебной информации, но не являются source of truth для proxy-ссылок.


### 8.4. Обслуживание

- Создаются health/deep-health проверки.
- Создаётся repair-команда для безопасного восстановления типовых проблем.
- Настраивается weekly maintenance с осторожной логикой, чтобы не ломать рабочую схему.

| sudo <prefix>-links | Показать все данные подключения: ссылки VLESS и Telegram, доступы к панели. |

| sudo <prefix>-repair --full | Полное восстановление: как repair, плюс восстановление базы 3x-ui (клиенты, inbound'ы, MTProto-секрет) из последнего снимка конфигурации, с подтверждением и авто-откатом при неудачной проверке (см. 19.3). |
| sudo <prefix>-weekly-maintenance.sh | Запустить еженедельное обслуживание вручную, не дожидаясь расписания. Может перезагрузить сервер — см. 19.2. |

```bash

```

Эта команда пригодится, если нужно сверить версию перед обновлением или приложить её к описанию проблемы.

### 9.1. Команды, которых больше нет

Если вы пользовались более ранними версиями XPAM, учтите: часть отдельных команд убрана, а их функции переехали в меню. Проверьте свои заметки и скрипты.

| Было | Стало |
|---|---|
| `<prefix>-status` | Меню → «Проверить состояние сервера» |
| `<prefix>-netdiag` | Меню → «Дополнительно / обслуживание» → «Диагностика сети Debian/провайдера» |
| `<prefix>-vless`, `<prefix>-tg` | `sudo <prefix>-links` — показывает и то, и другое |
| `<prefix>-links --show-secrets` | `sudo <prefix>-links` — теперь печатает всё сразу, отдельный флаг не нужен |

Обновление удаляет эти команды с сервера само, вручную ничего чистить не надо.

> [!CAUTION]
> Вывод <prefix>-links не копируйте в чаты и публичные логи: в нём реальные ссылки и пароли. Если нужно кому-то показать состояние — используйте <prefix>-links --safe.

## 10. Главное меню XPAM Script

Основной интерфейс открывается командой:

```bash
sudo <prefix>-xpam
```

Меню показывает то, что уместно на текущем этапе. **Пока сервер не установлен**, в нём только два пункта — чтобы не запутать:

| Пункт | Название | Назначение |
|---|---|---|
| 1 | SSH-безопасность и создание команды сервера | Первый обязательный шаг (см. главу 6). |
| 2 | Установить / продолжить настройку сервера | Основная установка (см. главу 7). |
| 0 | Выход | Закрыть меню. |

**После установки** пункты установки исчезают — они больше не нужны — и остаётся рабочее меню:

| Пункт | Название | Назначение |
|---|---|---|
| 1 | Показать данные для подключения | Ссылки VLESS и Telegram, адрес панели и доступы. |
| 2 | Проверить состояние сервера | Быстрая и глубокая проверка. |
| 3 | Telegram-уведомления | Оповещения о проблемах сервера. |
| 4 | WARP через 3x-ui/Xray | Выход отдельных сервисов через WARP, смена адреса, отключение. |
| 5 | DoubleHop Mode | Маршрутизация через Exit-сервер. |
| 6 | Управление сайтами | Сайты-маскировки и замена их своими. |
| 7 | Дополнительно / обслуживание | Обновления, диагностика, запасной транспорт, служебные действия. |
| 0 | Выход | Закрыть меню. |

Внутри пункта **«Дополнительно / обслуживание»**:

| Пункт | Назначение |
|---|---|
| 1 | Подробная диагностика состояния сервера. |
| 2 | Диагностика сети и особенностей провайдера. |
| 3 | Восстановление служебных настроек XPAM (repair). |
| 4 | Финальная production-очистка. |
| 5 | Показать текущую конфигурацию. |
| 6 | Проверить обновления XPAM. |
| 7 | Транспорты VLESS — запасной транспорт (глава 16). |
| 0 | Назад. |

Меню работает по принципу «команда → результат → возврат в оболочку»: вы выбираете действие, видите его вывод целиком и снова оказываетесь в командной строке. Чтобы выполнить следующее действие, откройте меню заново командой `sudo <prefix>-xpam`.

## 11. Где смотреть ссылки и секреты

После установки основная команда для данных подключения:

```bash
sudo <prefix>-links
```

Команда сразу показывает всё: ссылки VLESS и Telegram, адрес панели и доступы к ней. Отдельного флага для секретов не нужно — если вы уже вошли на сервер под root, эти данные вам и так доступны.

Если нужно посмотреть состояние при посторонних или приложить вывод к сообщению о проблеме, используйте краткую сводку без секретов:

```bash
sudo <prefix>-links --safe
```


### 11.1. Откуда берутся VLESS и Telegram links

Актуальные VLESS links и Telegram link берутся из текущей конфигурации 3x-ui. Это значит, что если пользователь добавил VLESS-клиента или поменял Telegram proxy / MTG secret в 3x-ui, повторный запуск <prefix>-links покажет уже актуальные данные.

| Данные | Источник | Комментарий |
|---|---|---|
| VLESS links | 3x-ui DB / текущие VLESS clients | Если клиент добавлен, удалён или переименован в 3x-ui, вывод должен отражать текущее состояние. |
| Telegram link | 3x-ui DB / текущий Telegram proxy / MTG inbound | Если secret изменён в 3x-ui, старая ссылка перестаёт работать, новая показывается через <prefix>-links. |
| Basic Auth | secure-notes | Доступ к странице панели. |
| 3x-ui login/password | secure-notes | Логин и пароль панели 3x-ui. |

> [!IMPORTANT]
> Не редактируйте вручную старые текстовые заметки для Telegram link. Актуальная Telegram-ссылка должна браться из 3x-ui через команду <prefix>-links.

## 12. VLESS, 3x-ui и Xray

VLESS в XPAM управляется через 3x-ui и Xray. Обычному пользователю чаще всего нужны две операции: скопировать ссылку существующего клиента или добавить нового VLESS-клиента.


### 12.1. Как безопасно получить VLESS-ссылку

Самый простой путь:

```bash
sudo <prefix>-links
```

В выводе найдите блок VLESS. Он покажет inbound name, client name и VLESS Link. Не отправляйте эту ссылку в публичные чаты.


### 12.2. Добавление клиентов

- Можно добавлять новых VLESS clients в существующий XPAM-managed VLESS inbound через 3x-ui.
- После добавления клиента запустите sudo <prefix>-links и убедитесь, что ссылка появилась.
- Если клиента удалили, его старая ссылка перестаёт работать — пользоваться ей уже нельзя.


### 12.3. Что не стоит менять в VLESS inbound

- Не меняйте port/listen/protocol XPAM-managed VLESS inbound без понимания последствий.
- Не меняйте TLS/security/fallback/externalProxy настройки базового inbound наугад.
- Не удаляйте базовый inbound, если не готовы восстанавливать схему через repair или переустановку.

<a id="ch13"></a>

## 13. Telegram proxy / MTG

Telegram proxy / MTG в текущей схеме управляется через 3x-ui. Пользователь получает одну Telegram link, которую можно добавить в Telegram-клиент.


### 13.1. Где взять Telegram link

```bash
sudo <prefix>-links
```

В выводе найдите блок Telegram link. Он имеет формат:

```text
tg://proxy?server=tg.example.com&port=443&secret=<redacted>
```

Скопируйте ссылку в Telegram на телефоне или компьютере. Ссылка должна открываться как proxy-настройка Telegram.


### 13.2. Ручная смена Telegram secret

Пользователь может вручную сменить Telegram proxy / MTG secret в 3x-ui, если понимает последствия. После смены старая Telegram link перестанет работать, а новая должна появиться в выводе:

```bash
sudo <prefix>-links
```

> [!NOTE]
> Смена secret штатным способом — это нормальная операция: проверки состояния и обслуживание из-за неё не ломаются, потому что XPAM всегда смотрит на текущую конфигурацию 3x-ui, а не на сохранённые ранее заметки.


### 13.3. Что не стоит менять

- Не меняйте port/listen/protocol Telegram proxy / MTG inbound без понимания последствий.
- Не отключайте нужный inbound в 3x-ui, если хотите, чтобы Telegram link работала.
- Не включайте route through Xray руками, если используете DoubleHop Mode через XPAM. DoubleHop должен управляться меню XPAM.

## 14. DoubleHop Mode

DoubleHop Mode настраивается на Entry-сервере. Exit-сервер не управляется XPAM автоматически: пользователь вручную создаёт или выбирает VLESS-клиента на Exit-сервере, копирует его VLESS link и вставляет эту ссылку в XPAM на Entry-сервере.


### 14.1. Что подготовить

1. На Exit-сервере создайте или выберите VLESS-клиента.
1. Скопируйте его VLESS link.
1. На Entry-сервере откройте sudo <prefix>-xpam -> DoubleHop Mode.
1. Вставьте Exit VLESS link, если XPAM её ещё не знает.


### 14.2. Режимы

| Режим | Что меняется |
|---|---|
| Только VLESS | VLESS-трафик Entry-сервера выходит через Exit-сервер. Telegram остаётся direct. |
| Только Telegram | Telegram proxy / MTG трафик выходит через Exit-сервер. VLESS остаётся direct. |
| VLESS + Telegram | Оба типа трафика выходят через Exit-сервер. |


### 14.3. Что важно пользователю

- Ваши ссылки VLESS и Telegram не меняются при включении и выключении DoubleHop — переподключать клиентов не нужно.
- Заворачивается **весь** VLESS-трафик выбранных режимов, включая запасной транспорт из главы 16, если он у вас включён.
- Если Exit-сервер недоступен, подключение через него перестанет работать; выключите DoubleHop — и всё вернётся к обычному прямому режиму.
- XPAM не заходит на Exit-сервер по SSH и ничего там не создаёт.
- Удаление сохранённой Exit-ссылки на Entry-сервере не удаляет клиента на самом Exit-сервере.

**DoubleHop и WARP.** Если у вас настроен WARP, при включении DoubleHop для VLESS он использоваться не будет: весь VLESS-трафик уходит через Exit-сервер, независимо от настроек WARP. Настройки WARP при этом сохраняются, и он снова заработает, как только вы выключите DoubleHop. Скрипт предупреждает об этом перед включением. В режиме «Только Telegram» VLESS остаётся прямым, поэтому WARP продолжает работать как обычно.


### 14.4. Как проверить после включения

```bash
sudo <prefix>-health
sudo <prefix>-health --deep
sudo <prefix>-links
```

Для VLESS можно дополнительно проверить внешний IP в клиенте. Для Telegram — проверить реальную работу Telegram link на телефоне или ПК.

## 15. WARP через 3x-ui/Xray

WARP — это бесплатный сервис Cloudflare, через который сервер может выходить в интернет от «чужого» адреса. В XPAM он используется точечно: **отдельные сайты идут через WARP, а весь остальной трафик — как обычно, напрямую**.

Зачем это нужно: некоторые сервисы плохо относятся к адресам дата-центров — показывают капчу, ограничивают качество видео или вовсе не открываются. Выход через WARP выглядит для них как обычный домашний пользователь.

> [!IMPORTANT]
> WARP здесь **не** системный VPN. Он не меняет маршрут сервера целиком: SSH, обновления, сертификаты, панель, ваши VLESS и Telegram продолжают работать напрямую и никак не зависят от WARP.


### 15.1. Как включить

```bash
sudo <prefix>-xpam
```

Выберите пункт **«WARP через 3x-ui/Xray» → «Настроить или проверить WARP outbound»**. Дальше всё происходит автоматически, **в панель заходить не нужно**:

1. Создаются ключи.
2. Регистрируется аккаунт WARP в Cloudflare.
3. Создаётся подключение к WARP и правило маршрутизации.
4. Перезапускается прокси-служба и выполняется проверка сервера.

По умолчанию через WARP направляются видеосервисы Google/YouTube — это готовый набор правил «из коробки». Остальной трафик идёт напрямую.

> [!NOTE]
> Перезапуск занимает несколько секунд, в этот момент активные подключения клиентов кратко обрываются и восстанавливаются сами.


### 15.2. Если регистрация не прошла

Иногда появляется сообщение, что сервер не смог связаться с Cloudflare. Это **не поломка XPAM и не блокировка вашего сервера**: у некоторых хостингов маршрут до адресов регистрации WARP просто не работает.

При этом никаких изменений в конфигурацию не вносится — сервер остаётся в прежнем рабочем состоянии. Если WARP принципиально нужен, самый простой путь — попробовать другого хостера: на одном провайдере регистрация не проходит, на другом отрабатывает за секунду.


### 15.3. Смена выходного адреса WARP

Если адрес, который выдал Cloudflare, начал ловить капчу или ограничения, его можно сменить:

**«WARP через 3x-ui/Xray» → «Сменить WARP-IP (новый выходной адрес)»**

Cloudflare выдаст новый адрес, XPAM приведёт настройки в порядок и перезапустит службу. Ваши ссылки VLESS и Telegram при этом не меняются.


### 15.4. Выключение

**«WARP через 3x-ui/Xray» → «Отключить WARP и вернуть VLESS в обычный режим»** — убираются подключение, правила маршрутизации и сохранённый аккаунт Cloudflare. Всё остальное продолжает работать как раньше.


### 15.5. Что важно знать

- WARP и DoubleHop — разные вещи и решают разные задачи. Если включён DoubleHop для VLESS, **весь** VLESS-трафик идёт через Exit-сервер, поэтому WARP при нём не используется (см. главу 14).
- Не ставьте системный WARP/VPN вручную поверх XPAM: маршруты начнут конфликтовать.
- Если вы добавляете собственные правила маршрутизации в панели, помните, что порядок правил важен — первое подходящее правило выигрывает.
- После любых изменений полезно выполнить `sudo <prefix>-health --deep`.

## 16. Запасной транспорт

Обычное подключение VLESS работает на основном домене и выглядит для сети как обычный HTTPS-сайт. Иногда провайдер или блокировки начинают мешать именно такому способу связи. На этот случай XPAM умеет поднять **запасной транспорт — второй вход на отдельном домене**.

Главное, что нужно понять: запасной транспорт **не заменяет основной и не трогает его**. Оба работают одновременно. Вы просто добавляете в приложение вторую ссылку и переключаетесь на неё, если первая перестала работать.

> [!NOTE]
> Это необязательная функция. Если основное подключение работает — она вам не нужна.


### 16.1. Когда это может пригодиться

- Основная ссылка перестала подключаться, хотя сервер жив и `<prefix>-health` не показывает проблем.
- Подключение работает нестабильно: то соединяется, то нет, особенно у одного конкретного провайдера или в мобильной сети.
- Вы хотите подготовить запасной транспорт заранее, чтобы не настраивать его в спешке.

Сначала стоит убедиться, что дело именно в способе связи, а не в сервере:

```bash
sudo <prefix>-health --deep
```

Если проверка зелёная, а клиент всё равно не подключается — запасной транспорт как раз для такой ситуации.


### 16.2. Что нужно подготовить

| Что | Зачем |
|---|---|
| Отдельный домен или поддомен | Например `cdn.example.com`. Он должен отличаться от основного, Telegram- и root-домена. |
| A-запись на IP этого сервера | Без неё не выпустится TLS-сертификат. |
| Открытый порт 80 | Нужен только на момент выпуска сертификата. |

Домен можно взять любой свободный — например поддомен, который выглядит как техническая часть сайта (`cdn.`, `static.`, `api.`).


### 16.3. Два варианта на выбор

XPAM предлагает два способа: **xhttp** и **grpc**. Оба прячут трафик внутри обычного HTTPS и внешне выглядят как работа с обычным сайтом — разница только в том, как именно устроен обмен данными внутри.

Что важно пользователю:

- Одновременно работает **только один** из них — они не складываются.
- Заранее сказать, какой окажется лучше именно у вашего провайдера, нельзя. Если один работает плохо, переключитесь на другой: XPAM сделает это автоматически, домен и сертификат переиспользуются.
- Клиентское приложение должно поддерживать выбранный способ. Современные клиенты поддерживают оба.


### 16.4. Как включить

```bash
sudo <prefix>-xpam
```

Дальше: **«Дополнительно / обслуживание» → «Транспорты VLESS»** и выберите xhttp или grpc. Скрипт спросит домен и всё остальное сделает сам:

1. Проверит, что домен указывает на этот сервер.
2. Выпустит TLS-сертификат.
3. Создаст на этом домене сайт-маскировку — он будет открываться как обычный сайт.
4. Поднимет подключение и покажет **отдельную ссылку** для клиента.

Добавьте эту ссылку в приложение как **второй сервер**. Основная ссылка при этом продолжает работать — удалять её не нужно.


### 16.5. Переключение и выключение

- **Сменить способ** (xhttp ↔ grpc) — тот же пункт меню, выберите другой вариант. Домен останется прежним, сертификат не перевыпускается, старое подключение снимается автоматически. **Ссылка изменится** — её нужно заново добавить в приложение.
- **Выключить** — пункт «Выключить» в том же меню. Уберутся подключение, маршрут и настройки. Основной домен и его ссылки не затрагиваются.

> [!IMPORTANT]
> Сертификат отдельного домена при выключении намеренно **не удаляется**. У Let's Encrypt есть ограничения на частоту выпуска, поэтому сохранённый сертификат позволяет включить запасной транспорт снова мгновенно и без риска упереться в лимит.


### 16.6. Что важно знать

- Маскировка работает и здесь: если открыть запасной домен в браузере, откроется обычный сайт, а не пустая страница или ошибка.
- Если включён DoubleHop, запасной транспорт тоже идёт через Exit-сервер — отдельно настраивать ничего не нужно.
- Основное подключение остаётся неизменным: те же ссылки, тот же домен, та же настройка.


### 16.7. Проверка после включения

```bash
sudo <prefix>-health --deep
```

Дополнительно откройте `https://<ваш-запасной-домен>/` в браузере — должен открыться обычный сайт. Затем проверьте подключение по новой ссылке в клиенте.

<a id="ch17"></a>

## 17. Сайты-маскировки

Чтобы сервер не выглядел как пустой технический endpoint, каждый домен открывается как обычный живой сайт. Это и есть маскировка — и работает она сразу, без вашего участия.


### 17.1. Что ставится по умолчанию

XPAM автоматически генерирует для каждого домена аккуратный сайт — лендинг небольшого технического продукта, с главной страницей, документацией, страницей лицензии и страницей 404. Название «продукта», оформление и вёрстка выводятся из имени домена, поэтому:

- **каждый сервер выглядит по-своему.** Отличается не только цвет — отличается сама страница: расположение блоков, тип иллюстрации, подача разделов, шрифтовое решение. Два сервера, установленные из одного и того же XPAM, не похожи друг на друга;
- **домены одного сервера тоже разные** — два ваших поддомена никогда не получат одинаковое оформление;
- **сайты выглядят живыми**: на страницах есть сдержанная анимация — например, мигающий курсор в окне терминала или плавно прорисовывающийся график. Никаких выдуманных «показателей», статусов и дат на сайтах нет, и со временем они не меняются;
- вам не нужно ничего настраивать — маскировка готова сразу после установки.

Одно и то же имя домена всегда даёт один и тот же сайт: после восстановления или переустановки оформление не «поедет».

> [!NOTE]
> Если вы включили запасной транспорт (глава 16), его домен тоже получает собственный сайт-маскировку — отличный от остальных.

> [!TIP]
> Самая убедительная маскировка — ваш собственный настоящий сайт. Если положить свои файлы в веб-корень домена, XPAM их сохранит (см. ниже).


### 17.2. Свой сайт вместо стандартного

Хотите поставить собственный сайт — просто положите его в веб-корень домена (`/var/www/<domain>/`, с файлом `index.html`). XPAM увидит его и не станет перезаписывать ни при установке, ни при repair.

Управление сайтами — в меню `sudo <prefix>-xpam` → «Управление сайтами». Там можно:

- посмотреть папки сайтов и правила их редактирования;
- загрузить свой сайт и применить его;
- вернуть стандартные сгенерированные страницы в любой момент.


### 17.3. Что нельзя занимать сайтом

Меняя оформление, не трогайте служебные пути — иначе сломаются сертификаты, панель или маршрутизация:

- путь панели 3x-ui;
- `/.well-known/acme-challenge/` — через него Let's Encrypt выдаёт сертификаты;
- служебные `location`/маршруты, которые использует XPAM.

После любой замены сайта проверьте, что всё в порядке:

```bash
sudo <prefix>-health
sudo <prefix>-health --deep
```

## 18. Telegram-уведомления

Telegram-уведомления присылают сообщение, если проверка состояния или еженедельное обслуживание завершились с ошибкой. Уведомления приходят **только при проблемах** — если всё прошло штатно, сообщений не будет. Это отдельная функция от Telegram proxy / MTG.


### 18.1. Что понадобится

- Bot token от BotFather.
- Chat ID пользователя, группы или канала, куда бот должен писать.
- Проверка, что VPS может отправить HTTPS-запрос к Telegram API или к настроенному relay.


### 18.2. Как включить

Откройте меню:

```bash
sudo <prefix>-xpam
```

Выберите пункт Telegram-уведомления и следуйте подсказкам. Если уведомления не нужны, этот шаг можно пропустить.

> [!IMPORTANT]
> Telegram-уведомления не нужны для работы VLESS или Telegram proxy / MTG. Это только эксплуатационный alerting.

<a id="ch19"></a>

## 19. Health-check, repair и обслуживание


### 19.1. Быстрая и глубокая проверка

```bash
sudo <prefix>-health
sudo <prefix>-health --deep
```

Быстрая проверка отвечает на вопрос: сервер в целом живой или нет. Глубокая смотрит подробнее — службы, порты, конфигурацию, сертификаты, ссылки, маршрутизацию, состояние DoubleHop и WARP, работу сайтов-маскировок, а также запас памяти и места на диске.

Глубокую проверку стоит запускать после установки, обновления, восстановления и любых изменений DoubleHop, WARP или запасного транспорта.


### 19.2. Еженедельное обслуживание

XPAM сам настраивает регулярное обслуживание — оно запускается по расписанию раз в неделю, ночью в воскресенье, и не требует вашего участия. За один проход выполняется:

- снимок текущей конфигурации (чтобы было к чему вернуться);
- обновления системы — **все доступные, включая обновления ядра**;
- продление TLS-сертификатов;
- проверка состояния сервера;
- уборка старых логов и резервных копий по заданным лимитам.

Ваши ссылки VLESS и Telegram при этом не меняются, а настройки DoubleHop и WARP не сбрасываются.

> [!IMPORTANT]
> **Если установленное обновление требует перезагрузки, сервер перезагрузится сам.** Обычно это обновление ядра. Перезагрузка занимает меньше минуты, происходит ночью и не требует вашего участия, но в этот момент подключения клиентов кратко обрываются.

После такой перезагрузки XPAM автоматически выполняет второй проход: дожидается запуска служб, доустанавливает то, что стало доступно после первой партии обновлений, прибирает за собой и проверяет состояние сервера. Этот проход одноразовый — он выполняется ровно один раз после перезагрузки и на следующих загрузках уже не запускается.

Сообщение в Telegram (если уведомления настроены) приходит **только если что-то пошло не так**. Молчание означает, что обслуживание прошло штатно.

Если автоматическая перезагрузка вам не подходит — например, сервер нельзя ронять без предупреждения, — режим обновлений меняется параметром `XPAM_MAINT_APT_MODE` в `/etc/xpam-script/config.env`:

| Значение | Поведение |
|---|---|
| `auto` (по умолчанию) | Ставит все обновления, включая ядро, и перезагружает сервер, если это нужно. |
| `upgrade` | Обычное обновление пакетов: ядро придерживается, сервер **сам не перезагружается**. |
| `off` | Обновления системы не ставятся совсем. Тогда обновлять сервер придётся вручную. |

Настройка читается при каждом запуске обслуживания, поэтому достаточно сохранить файл — перезапускать или чинить ничего не нужно.

> [!NOTE]
> Значение `security` не используйте: это старое имя того же режима, что и `upgrade`, и XPAM при обновлении заменяет его на `auto`. Чтобы отключить автоматическую перезагрузку, нужно именно `upgrade`.

Запустить обслуживание вручную, не дожидаясь расписания:

```bash
sudo <prefix>-weekly-maintenance.sh
```

В конце вывода будет строка `Status: OK`, если всё прошло штатно, и путь к подробному журналу.


### 19.3. Repair

Repair нужен для типовых проблем, но не является заменой внимательной диагностики. Запускайте его, если health/deep-health показывает проблему или после неудачной ручной правки.

```bash
sudo <prefix>-repair
sudo <prefix>-health
sudo <prefix>-health --deep
```

> [!NOTE]
> Repair не трогает корректно изменённый Telegram secret и не берёт ссылку из старых текстовых заметок — источником всегда остаётся текущая конфигурация 3x-ui.

Обычный repair, помимо прочего, заново собирает конфигурацию nginx.

**Полное восстановление базы.** Команда `sudo <prefix>-repair --full` дополнительно восстанавливает базу 3x-ui (клиенты, inbound'ы, MTProto-секрет) из последнего снимка конфигурации: проверяет целостность базы, запрашивает подтверждение — нужно ввести дословно `restore-full`, — создаёт резервную копию текущей базы и автоматически откатывается, если проверка состояния после восстановления не проходит.

> [!IMPORTANT]
> `repair --full` возвращает базу к состоянию на момент снимка. Если вы включили запасной транспорт (глава 16) уже **после** того, как снимок был сделан, его подключение из снимка не восстановится: настройки XPAM останутся, а самого подключения в базе не будет. Скрипт предупредит об этом до подтверждения. Включите транспорт заново через меню — ссылка запасного транспорта при этом обновится, её нужно будет заново добавить в клиент. Основные ссылки VLESS и Telegram это не затрагивает.

## 20. Безопасное обновление XPAM

XPAM обновляется из меню, одним действием. Обновляется только сам XPAM — 3x-ui, Xray и системные пакеты живут своей жизнью.

Порядок такой: скрипт скачивает опубликованный релиз, сверяет его контрольную сумму, делает резервную копию текущей версии, применяет новую, проверяет состояние сервера — и, если проверка не прошла, **сам возвращает предыдущую версию**. Отдельно сверяется, что ссылки подключения после обновления не изменились.


### 20.1. Как запустить проверку обновлений

```bash
sudo <prefix>-xpam
```

Дальше: **«Дополнительно / обслуживание» → «Проверить обновления XPAM»**. Не обновляйте XPAM случайными командами из чатов, минуя эту проверку.


### 20.2. Что сохраняется при обновлении

- Ваши VLESS-клиенты и их ссылки.
- Telegram proxy / MTG: секрет и ссылка из 3x-ui.
- Настройки DoubleHop: сохранённая ссылка Exit-сервера и выбранный режим.
- Настройки WARP и запасного транспорта.
- Ваш собственный сайт, если вы поставили его вместо стандартного.
- Команды `<prefix>-xpam`, `<prefix>-links`, `<prefix>-health`, `<prefix>-repair` и еженедельное обслуживание.

Переподключать клиентов после обновления не нужно.


### 20.3. После обновления

```bash
sudo <prefix>-health
sudo <prefix>-health --deep
sudo <prefix>-links
```

> [!WARNING]
> Если обновление завершилось с rollback, не пытайтесь вручную добить частично применённые файлы. Сначала сохраните лог и проверьте health.

<a id="ch21"></a>

## 21. Что можно менять в 3x-ui, а что относится к базовой схеме XPAM

XPAM не блокирует ручную работу в 3x-ui. 3x-ui остаётся панелью управления, но XPAM гарантирует только свою базовую схему. Всё, что вы добавляете сверх неё, — на вашей стороне: следите, чтобы это не конфликтовало с портами, доменами, сертификатами и правилами маршрутизации, которыми управляет XPAM.


### 21.1. Что можно делать

- Смотреть статистику, трафик и состояние клиентов.
- Копировать текущие VLESS и Telegram links.
- Добавлять, отключать и удалять VLESS clients в существующем VLESS inbound.
- Переименовывать clients и display remarks.
- Добавлять user-managed inbounds, если они не конфликтуют с портами и доменами XPAM.
- Добавлять собственные outbounds/routing rules, если вы понимаете порядок правил Xray.
- Вручную менять Telegram proxy / MTG secret, если готовы обновить ссылку в Telegram-клиенте.


### 21.2. Что относится к базовой схеме XPAM

- XPAM-managed VLESS inbound port/listen/protocol.
- TLS/security/fallback/externalProxy настройки XPAM-managed VLESS inbound.
- Telegram proxy / MTG inbound port/listen/core settings.
- 3x-ui panel listen/port/base path/cert paths.
- HAProxy/nginx/certbot wiring.
- XPAM routing rules/outbounds/tags.
- DoubleHop routing. Его лучше менять через меню XPAM, а не руками в 3x-ui.
- Запасной транспорт (глава 16): его подключение, отдельный веб-front и маршрут по имени домена.


### 21.3. Что делать после ручных изменений

```bash
sudo <prefix>-health
sudo <prefix>-health --deep
sudo <prefix>-links
```

Если меняли только VLESS clients, обычно достаточно проверить links и подключение клиента. Если меняли inbound/listen/port/TLS/routing, проверяйте глубже и будьте готовы откатить изменения.

<a id="ch22"></a>

## 22. Частые проблемы и диагностика


### 22.1. Не входит по SSH после шага 1

- Проверьте, что используете private key, а не public key.
- Проверьте, что public key лежит в /root/.ssh/authorized_keys одной строкой.
- Проверьте права: /root/.ssh = 700, authorized_keys = 600.
- Если старая SSH-сессия ещё открыта, исправьте ключ через неё.


### 22.2. Certbot не выдаёт сертификат

- Проверьте A-записи доменов на SERVER_IP.
- Проверьте, что TCP 80 открыт и не занят чужим сервисом.
- Проверьте, что DNS уже распространился.

```bash
nslookup example.com
```


### 22.3. Панель 3x-ui отвечает HTTP 401

HTTP 401 на странице панели означает, что сработал Basic Auth. Введите Basic Auth username/password из вывода <prefix>-links, затем логин/пароль самой 3x-ui панели.


### 22.4. VLESS не подключается

- Скопируйте ссылку заново через <prefix>-links.
- Проверьте, что клиент поддерживает VLESS/TLS/flow, указанные в ссылке.
- Проверьте health/deep-health.
- Если вручную меняли inbound в 3x-ui, откатите изменения или запустите repair.


### 22.5. Telegram link не работает

- Скопируйте текущую ссылку заново через <prefix>-links.
- Если недавно меняли secret в 3x-ui, старая ссылка больше не работает.
- Проверьте health/deep-health.
- Проверьте, что Telegram domain указывает на SERVER_IP.


### 22.6. DoubleHop включён, но трафик не выходит через Exit

- Проверьте, что Exit VLESS link рабочая сама по себе.
- Проверьте статус DoubleHop в меню XPAM.
- Запустите health/deep-health.
- Выключите DoubleHop и убедитесь, что direct-режим восстановился.


### 22.7. sudo пишет unable to resolve host

Обычно это проблема hostname и /etc/hosts. XPAM старается нормализовать её на шаге 1/repair. Проверьте:

```bash
hostname
cat /etc/hosts
sudo <prefix>-repair
```


### 22.8. Команда links не показывает ожидаемую ссылку

- Проверьте, что смотрите полную версию: <prefix>-links.
- Проверьте, что VLESS client или Telegram inbound реально включены в 3x-ui.
- Запустите deep-health.
- Не ищите Telegram link в старых secure-notes: актуальный источник — текущая 3x-ui конфигурация.


### 22.9. Подключение перестало работать, хотя сервер в порядке

Ситуация: `sudo <prefix>-health --deep` показывает, что всё хорошо, домены открываются в браузере, но клиент не подключается — или подключается через раз, обычно у одного провайдера или в мобильной сети.

Скорее всего дело не в сервере, а в том, как до него идёт связь. Порядок действий:

1. Проверьте, работает ли подключение через другую сеть (например, раздать интернет с телефона). Если через другую сеть работает — проблема в сети провайдера.
2. Обновите ссылку: `sudo <prefix>-links` — и добавьте её в клиент заново.
3. Включите **запасной транспорт** (глава 16) и добавьте его ссылку в клиент вторым сервером.
4. Если запасной транспорт на xhttp работает плохо — переключитесь на grpc (или наоборот): что лучше идёт у конкретного провайдера, заранее не известно.

Основное подключение при этом остаётся на месте: вы просто получаете второй вход и пользуетесь тем, который работает.


### 22.10. На домене открывается незнакомый сайт какого-то продукта

Так и должно быть. Это сайт-маскировка (глава 17): XPAM генерирует для каждого домена правдоподобный сайт, чтобы сервер выглядел как обычный веб-проект, а не как пустой технический адрес. Название «продукта» и оформление придуманы автоматически и у каждого сервера свои.

Если хотите — поставьте вместо него свой настоящий сайт, XPAM его не тронет (см. 17.2).


### 22.11. WARP не удалось зарегистрировать

Сообщение о том, что сервер не смог связаться с Cloudflare, означает, что у хостинга не работает маршрут до адресов регистрации WARP. Это не поломка XPAM и не блокировка вашего сервера: конфигурация при этом не меняется, всё остальное продолжает работать. Подробнее — в разделе 15.2.

## 23. Диагностика сети и особенности VPS-провайдеров

VPS-провайдеры заметно отличаются друг от друга: настройками DNS, firewall, поддержкой IPv6, состоянием пакетной системы. XPAM учитывает типовые особенности, но базовые проверки полезно уметь делать самостоятельно.


### 23.1. Диагностика сети

Отдельной команды для этого нет — проверка вызывается из меню:

```bash
sudo <prefix>-xpam
```

Дальше: **«Дополнительно / обслуживание» → «Диагностика сети Debian/провайдера»**.

Что она делает:

- проверяет, работает ли определение имён (DNS);
- проверяет доступность важных внешних адресов;
- помогает понять, где именно проблема: в самом VPS, в DNS, в доступе к GitHub, Telegram или Let's Encrypt — или уже на стороне вашего клиента.


### 23.2. Особенности отдельных провайдеров

- Некоторые VPS приходят с грязным apt/dpkg состоянием. XPAM проверяет это перед тяжёлыми операциями.
- На Debian может не быть systemd-resolved. Это нормально; DNS проверяется доступными средствами.
- На Ubuntu ssh.socket может влиять на SSH listener. XPAM учитывает это в своей SSH-политике.
- Если провайдер фильтрует 80 или 443, certbot или proxy-схема не заработают без исправления на стороне провайдера.

<a id="ch24"></a>

## 24. Финальная production-очистка

После успешной установки и проверки можно выполнить production cleanup. Он убирает временные установочные файлы и оставляет только рабочие команды, конфигурацию, secure-notes и логи, которые нужны для эксплуатации.


### 24.1. Что можно удалить

- Временные архивы установки в /root, если они больше не нужны.
- Старые распакованные каталоги установщика.
- Временные тестовые файлы, если они не нужны для диагностики.


### 24.2. Что нельзя удалять

- /etc/xpam-script
- /opt/xpam-script
- /etc/x-ui/x-ui.db
- /root/secure-notes с паролями и доступами
- Let's Encrypt certificates и nginx/HAProxy конфигурацию


### 24.3. Перед закрытием работ

```bash
sudo <prefix>-health
sudo <prefix>-health --deep
sudo <prefix>-links
```

> [!WARNING]
> Сохраните секреты в парольный менеджер. Не оставляйте единственную копию паролей только на VPS.

<a id="ch25"></a>

## 25. Чек-лист готового сервера


### 25.1. До установки

- SSH-ключ создан.
- Вход по private key проверен отдельной новой SSH-сессией.
- DNS A-записи указывают на SERVER_IP.
- TCP 22, 80, 443 доступны.
- VPS чистый и не содержит чужой production-конфигурации.


### 25.2. После установки

- <prefix>-xpam открывает меню.
- Основная команда управления — <prefix>-xpam.
- <prefix>-links показывает актуальные ссылки VLESS и Telegram и доступы к панели.
- <prefix>-health проходит без ошибок.
- <prefix>-health --deep проходит без ошибок (допустимы понятные предупреждения).
- VLESS-клиент подключается.
- Telegram link работает в Telegram-клиенте, если профиль включает Telegram proxy / MTG.
- Панель 3x-ui открывается только через правильный путь и Basic Auth.
- DoubleHop выключен, если вы его не используете, или включён в нужном режиме, если используете.
- Если включали запасной транспорт (глава 16) — его домен открывается в браузере как обычный сайт, а вторая ссылка добавлена в клиент.
- Секреты сохранены в безопасном месте.


### 25.3. Перед публикацией скриншотов или issue

- Удалите VLESS links, Telegram links, Basic Auth, 3x-ui password, UUID, tokens и реальные домены/IP, если они не должны быть публичными.
- Используйте placeholders: SERVER_IP, example.com, vless.example.com, tg.example.com, <prefix>, <redacted>.

> [!NOTE]
> Готовый сервер — это не только успешная установка. Это сервер, у которого проверены клиенты, ссылки, health, deep-health, доступы, обновление и понятный план восстановления.
